## Решение

### Часть 10.1 — Анализ критически важных данных

#### Данные для миграции в Cassandra:

**Заказы (orders)**

- **Целостность**: Критична - ошибки ведут к финансовым потерям
- **Скорость**: Высокая требовательность к записи и чтению
- **Обоснование для Cassandra**: Высокая скорость записи, отказоустойчивость, линейная масштабируемость

**Корзины (carts)**

- **Целостность**: Высокая - конфликты данных при оформлении заказов
- **Скорость**: Минимальная задержка при операциях пользователя
- **Обоснование**: Быстрое обновление состояния, высокая доступность

**Пользовательские сессии (sessions)**

- **Целостность**: Средняя - потери сессий восстанавливаемы
- **Скорость**: Минимальная задержка аутентификации
- **Обоснование**: Высокая скорость записи/чтения, TTL поддержка

#### Данные для сохранения в MongoDB:

**Товары (products)**

- **Причина**: Сложные запросы по категориям, агрегации, полнотекстовый поиск
- **Обоснование**: MongoDB лучше подходит для каталога товаров

**История заказов (order_history)**

- **Причина**: Аналитические запросы, агрегации по датам
- **Обоснование**: MongoDB эффективнее для аналитики

### Часть 10.2 — Концептуальная модель Cassandra

#### Таблица заказов (orders)

```sql
CREATE TABLE orders (
    order_id UUID,
    customer_id UUID,
    order_date TIMESTAMP,
    status TEXT,
    total_amount DECIMAL,
    items LIST<FROZEN<order_item>>,
    PRIMARY KEY ((order_id), order_date)
) WITH CLUSTERING ORDER BY (order_date DESC);
```

- **Partition key**: `order_id` - равномерное распределение
- **Кластерный ключ**: `order_date` - сортировка по времени

#### Таблица корзин (carts)

```sql
CREATE TABLE carts (
    user_id UUID,
    cart_id UUID,
    created_at TIMESTAMP,
    updated_at TIMESTAMP, 
    items MAP<UUID, INT>,
    expires_at TIMESTAMP,
    PRIMARY KEY ((user_id), cart_id)
) WITH default_time_to_live = 86400;
```

- **Partition key**: `user_id` - изоляция данных пользователя
- **TTL**: Автоматическое удаление старых корзин

#### Таблица сессий (user_sessions)

```sql
CREATE TABLE user_sessions (
    session_token UUID,
    user_id UUID,
    created_at TIMESTAMP,
    last_activity TIMESTAMP,
    user_data TEXT,
    PRIMARY KEY ((session_token))
) WITH default_time_to_live = 3600;
```

- **Partition key**: `session_token` - равномерное распределение
- **TTL**: Автоматическое истечение сессий

### Защита от "горячих" партиций:

- Использование UUID вместо последовательных ID
- Равномерное распределение по токенам партиций
- Мониторинг размера партиций

### Часть 10.3 — Стратегии обеспечения целостности

#### Hinted Handoff

- **Применение**: Заказы, корзины
- **Уровень консистентности**: QUORUM
- **Обоснование**: Гарантия записи при временной недоступности узлов

#### Read Repair

- **Применение**: Корзины, сессии
- **Уровень консистентности**: LOCAL_QUORUM
- **Обоснование**: Быстрое чтение с автоматическим исправлением

#### Anti-Entropy Repair

- **Применение**: Все таблицы (периодически)
- **Расписание**: Ежедневно в низконагрузочное время
- **Обоснование**: Гарантия долгосрочной консистентности

## Последствия

### Положительные:

- Линейная масштабируемость при росте нагрузки
- Высокая доступность в режиме 24/7
- Быстрое добавление узлов без простоя

### Отрицательные:

- Сложность миграции и обучения команды
- Ограничения на сложные запросы
- Необходимость дублирования данных для аналитики
